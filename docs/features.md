# Features

What the page shows, view by view. For running the tool, see the [README](../README.md) and [usage.md](usage.md).

The browser's Back and Forward buttons move between what you looked at: each tab you switch to, each item a link jumped to further down a page, and each item opened on the canvas or in the call view. Back returns to where the page was scrolled. Stepping through the review with **Next ▸**, `j` or `k` adds one entry, not one per step, so that Back returns to where the steps started. The address shows the current place (`#/module/…`, `#/module/…/item/…`), so a link to it opens the page there.

The view buttons, names and **Open ▸**, **Canvas ▸** and **Internal call graph ▸** buttons are links to such addresses, so a middle click or Ctrl+click (⌘+click) opens them in a new tab, for example to follow several call graphs side by side. A call graph laid out on the canvas has an address of its own (`#/graph/…`, `#/module-graph/…`, `#/impact/…`), which a new tab lays out again; the **Canvas** button opens the cards that the canvas shows now, laid out by module. Review marks made in one tab show up in the other tabs of the page right away.

## Overview

Shows the PR's changed call graphs, then its public API changes as a compact list. The full entries, with their rustdoc-style signature diff, docs and every reason for their label, are on the module pages, so the overview doesn't show the same items twice.

Public items are found where rustdoc documents them: at their definition path when that is public, otherwise at a re-export (a `#[doc(inline)]` re-export first, a `#[doc(no_inline)]` one last). Items marked `#[doc(hidden)]`, or reachable only through hidden modules or hidden `pub use`s, are not part of the public API; an item that becomes hidden shows as "no longer public". Items of other crates that a crate re-exports (`pub use serde::Serialize;`) are part of its API too, so adding, removing or retargeting such a `pub use` is an API change.

**Changed call graphs**, above the public API, sums up the PR as the call graphs it adds or changes rather than the files it touches, e.g. "2 graphs · 9 functions changed, 3 new". A graph starts at a changed function that no other changed function calls (its root) and lists the changed functions the root reaches, in call order and indented by call depth, with new ones marked. A call through one unchanged item still counts (shown as "`encode` via `save`"), so that a small unchanged wrapper doesn't split a graph. Graphs that share a changed function are merged, so every function is listed once; a graph with several roots names them all in its heading. Types and constants don't merge graphs, since a widely used type would otherwise join the whole PR into one: each graph lists the changed ones its functions use. Each graph also says where it is reached from, the public items or uncalled functions such as `main` above its roots ("Reached from `start` via `load`"), and which test functions reach it, as a list: changed ones and the changed test helpers they call first, unchanged ones folded. **Canvas ▸** opens the graph's functions on the canvas; on a phone, **Calls ▸** opens its root in the call view. Each graph is a card whose parts are labeled on the left ("Public API", "Reached from", "Calls", "Types and constants", "Tests"; stacked on a phone), with a guide line per call depth. A public item that needs attention carries its SemVer label (**⚠ breaking** or **? check by hand**) wherever a graph lists it; non-breaking changes get none, so that those stand out. Changed tests that reach no graph (and helpers no such test calls), changed types no graph uses and removed items are listed at the end. Only resolved calls are followed: a function called only through a trait or from inside a macro starts a graph of its own, which says it has no resolved caller. A changed function that dispatches to many others (a click handler, a render function) joins what it calls into one large graph, whose size then shows in its heading.

**Impact of internal changes**: on an item's row on its module page and on its canvas card, an added or changed item outside the public API gets a line with the public items that reach it through calls and uses ("Affects public API: `evaluate` via `apply`"). Each chain stops at its first public item. Hovering a public item shows its whole chain, and **Show on canvas ▸** opens every chain on the canvas, callers above what they call. When no chain exists, it says so: for a method of a trait impl, calls through the trait are not followed, and unresolved call sites can hide a chain, which the note then mentions. Removed items, modules and impls get no impact line.

**Unsafe code** is listed first, in a box with a striped yellow and black edge, when the PR adds, changes or removes any: `unsafe` blocks, functions, impls and traits, `extern` blocks (with or without `unsafe`), and attributes that are unsafe to use (`#[unsafe(…)]`, `#[no_mangle]`, `#[export_name]`, `#[link_section]`). Each item or piece of code outside items gets a row with what changed: "new `unsafe` block, line 59", "`unsafe fn read` changed", "`unsafe impl Send for Buf` removed". Wherever items are listed (item rows, canvas cards and their member lists, the call view, the module map, search results, tooltips) such an item carries a yellow **⚠ unsafe** tag, or a quieter "unsafe removed" if it only removes `unsafe` code, and its rows and cards list the changes. In source diffs, the lines of each changed piece get a hazard stripe on the left and a note on their first line. The detection works on tokens, so it also finds `unsafe` code inside macro arguments and `macro_rules!` bodies, and comments (such as `// SAFETY:`) are not compared. An `unsafe fn` counts as one piece, its whole body included, since its body may do unsafe operations. Safe code that unsafe code relies on (a length field that an `unsafe` block trusts) is not flagged.

Sections without changes are left out, on the overview and on the module pages. What a section lists is explained on hover over the **?** next to its heading, not in an intro paragraph.

Each public API change is labeled **breaking**, **non-breaking** or **check by hand**, following [Cargo's SemVer rules](https://doc.rust-lang.org/cargo/reference/semver.html), with the reasons listed under the label (and on hover). The top of the section counts them and names the version each crate needs, from its version in the base's `Cargo.toml` (`0.3.1 → 0.4.0` for a breaking change, `1.4.2 → 1.5.0` for a compatible one), and says whether the version the PR sets is enough. Crates with `publish = false`, new crates and pre-release versions get the general rule instead ("a major version bump, minor before 1.0"). The base's version may already be an unreleased bump, so the page compares with it and says so on hover. Breaking, for example: removing an item or one of its public paths, adding a variant to an enum that isn't `#[non_exhaustive]`, adding any field to a struct whose fields are all public, a changed function signature, a function that is no longer `const` or is now `unsafe`, a new trait item without a default, a new supertrait, a trait no longer derived. Non-breaking: new items and paths, a newly derived trait, new fields next to private ones, a type parameter with a default, `const` added, `unsafe` removed, a changed constant value. "Check by hand" is for what the definitions can't settle: a changed macro, `#[repr]` or enum discriminant. Body and doc changes are no API change. Members of trait impls are labeled with their impl.

Under the counts, every public API change is listed by its public path, with its label and its first reason: breaking ones first, then those to check by hand, the non-breaking ones and the allowed breaking ones (the last two folded after 10). A click shows the item on its module page (an unchanged item that only cargo-semver-checks labeled: on the canvas). Changes to a public function's body or docs only are no API change and are not listed; the call graphs show them. Links to an item on the overview (`#/overview/item/…`, as in older PR comments) open its module page.

Crates that don't follow SemVer on purpose, such as internal crates, can allow breaking changes in their `Cargo.toml`:

```toml
[package.metadata.rust-semantic-review]
allow-breaking-changes = true
```

Their breaking changes are then labeled "breaking (allowed)" in a muted style, counted apart, left out of the list of breaking changes and of the version the crate needs, and the summary names the crates that allow them. The setting is read from the base's `Cargo.toml`, so that a PR can't silence the warning about its own breaking change: a PR that adds it gets a note that it applies once merged.

With `--semver-checks`, cargo-semver-checks' findings are added to these labels. It sees what the definitions alone don't: auto traits (a type that is no longer `Send` or `Sync` because of a change elsewhere), trait impls that derives and macros generate, items behind `cfg`s. Each finding is matched to its item by the file and line it points at (and the name there), or else by its public path. A finding that needs a bigger version bump than the label says raises the label and adds a reason, marked with the lint's id; so does one on an item without a label, which then appears in the overview even if its code is unchanged. A finding the label already covers is listed as "✓ cargo-semver-checks agrees". Under the counts, a line says which version ran, how many lints and how long it took, and lists findings that match no item. If it can't check the PR (the code doesn't build, a rustdoc JSON format it doesn't know), the page says so and shows its error, and the labels come from the definitions alone. `fixtures/semver-gaps` is an example: a private field's type change makes a public type lose `Send` and `Sync`, which the definitions don't show. It also removes a `#[derive(Hash)]`, which the definitions label too; there cargo-semver-checks agrees.

The sidebar lists the modules that changed or contain changes, with a status symbol and the number of changed items in each. Unchanged modules are left out (except the open module and its parents); **show unchanged modules** lists them too. When the PR changes no Rust item, the module tree is left out, except on the module pages, where it is the way to browse the modules.

Below the modules, the sidebar lists every changed file with its status and its added and removed lines (the total is in the heading). A Rust file whose changes are all inside items opens its module's page; any other file scrolls to its entry in the overview.

On the canvas and in the call view, the sidebar shows the call graph instead (when the PR has a changed call graph): the changed call graphs that the cards on the canvas (or the call view's focused item) belong to, as call trees like in the overview, with a guide line per call depth and the types and constants they use. Everything in a graph is changed, so only new and removed items are marked. In review mode, each row shows its verdict (✓ approved, ✗ changes requested, ✎ commented, ↻ changed since the review), and each graph's heading counts what is left. On the canvas, names in gray italics have no card yet: a click opens one next to its caller, a click on any other name shows its card, and hovering a name outlines its card. Below come the other cards on the canvas and the other call graphs, which open on the canvas with a click. In the call view, a click focuses the item.

**«** at the sidebar's top right hides it, and **»** on the thin strip left in its place shows it again. This is remembered per view, so the sidebar can be hidden on the canvas but kept on the module pages. On a narrow screen, the sidebar is a drawer that the ☰ button opens.

## Changed files

Every file the PR changes is accounted for:
- **Dependencies and package settings**, at the top: changes in each `Cargo.toml` as entries (dependencies in every section, including target-specific ones, features, workspace members, package version, edition and minimum Rust version), not as text. Lock files (`Cargo.lock`, `uv.lock`, `poetry.lock`) are listed there too, as the packages whose locked version changed: updated (labeled breaking or compatible by Cargo's semver rules, or major, minor or patch for Python, and downgrades), added and removed. A package that keeps its version but now comes from another source (a git repository instead of the registry) or has another checksum is flagged, since the code it stands for changed. For `Cargo.lock`, each package is marked as a workspace crate, a direct dependency (of a workspace crate or path dependency) or a transitive one, with the packages that require it, and a line above the list counts the new and removed dependencies, highlighting new transitive ones. Crates from crates.io link to the published code on [diff.rs](https://diff.rs): the diff between the two versions for an update, the source for a new crate. New crates also show their description and whether they run code at build time (a build script or a procedural macro). Updates and new crates link the changelog in the published package (on docs.rs) or else the repository. That metadata comes from the crates' sources that Cargo downloaded for the analysis; nothing is fetched for it, so it is missing for crates Cargo didn't download (e.g. with `--syntax-only` and an empty Cargo cache), and the page works offline.
- **Changed files**, at the end: each changed file with its +/− counts, sorted by language or kind (Rust code outside items, Python, JavaScript, CSS, YAML, Docs, package files, other files), with a heading per group when some group has several files. A Rust file whose changes are all in items is left out, since the item sections show it. **Next** goes through the files in the same order.
  - **Python** files are compared by function and class (nested ones under their `__qualname__`, e.g. `Corpus.build` or `f.<locals>.g`). For each one: added, removed, or what changed: the header (diffed), the docstring, the body; changes in only whitespace or comments are marked as such. Changes to top-level statements are noted. A small tokenizer tracks strings, comments, brackets and line continuations, so that `def` inside a string or a bracket is never taken for a definition.
  - **Markdown** files are compared section by section (headings outside code fences): changed paragraphs are marked as in doc comments, with word-level marks where safe, added sections get a bar, removed headings are struck through, and unchanged sections are counted.
  - **JavaScript** files (`.js`, `.mjs`, `.cjs`, `.jsx`) are compared by function, class and method: function declarations and `const f = (…) => …`, classes with their methods, getters, setters, fields and static blocks (`Cart.add`), other top-level `const`/`let`/`var` declarations, and test blocks (`describe("Cart") › it("counts items")`, any top-level call whose first argument is a string, with such calls in its callback nested under it). For each one: added, removed, or what changed: the header (diffed), the JSDoc comment, the body; changes in only whitespace or comments are marked as such. Changes to other top-level code (imports, statements) are noted. A tokenizer follows strings, template literals with their `${…}` expressions, regular expression literals and comments, so braces inside them don't count. Diffs have syntax colors.
  - **YAML** files (`.yml`, `.yaml`), such as GitHub Actions workflows, are compared by key: each top-level key is a box, and a long block (over 12 lines) is split into its child keys or list items, down to four levels. List items are named by their `name:`, `id:` or `uses:` (a workflow's `jobs.test.steps[Build]`), or else by their position. Changes in only whitespace or comments are marked as such. Their diffs have syntax colors: keys, strings, numbers, booleans, comments, anchors and tags, and `${{ … }}` expressions wherever they appear; block scalars (`run: |`) are followed across lines, so a script's lines aren't taken for keys.
  - **CSS** files are compared by selector. The stylesheet is parsed into rules (following comments, strings, brackets, at-rules and native `&` nesting), and the declarations of every rule for the same selector in the same `@media`/`@supports`/… context are merged by the cascade: a later declaration wins unless an earlier one is `!important`. Each changed selector is a box listing its added, changed and removed properties, with the other properties it keeps for context, and the lines of the rules it was merged from. A declaration that changed without changing what applies (one a later rule overrides) is shown with why it has no effect. Selectors of one rule that changed the same way share a box (`h1, h2`); `@import` and other statements are boxes of their own. Changes in only comments or formatting are noted as such. Their diffs have syntax colors: selectors, properties, numbers and colors, strings, at-rules and comments.
  - **Rust code outside items**: in a Rust file whose items are analyzed, the code that belongs to no item (macro calls such as `thread_local!`, `extern` blocks) gets a box per macro call or block. Each box shows the header with its attributes and the diff of its lines; doc comment and formatting-only changes are marked. The file's card links its module's page for the items themselves.
  - **Other text files** show a line diff (shown directly when small).
  - **Binary** and very large files (over 1 MB) are listed without a diff.
  - **Generated and vendored** files (lock files, `vendor/`, `third_party/`, `node_modules/`, minified files, files marked `@generated` or "do not edit") are collapsed into one group.
- A PR without any Rust change says so instead of showing empty sections.

## Items

Every item shows what rustdoc would show: its definition or signature (private fields hidden when looking from outside the module), its docs, and its place in the module tree. A type's definition also shows its `#[derive(…)]`, with the traits sorted: rustdoc lists derived traits among the impls, which the syntactic pass doesn't see, so a derive that was added or removed shows here (reordering them is no change).

- **Change markers**: inside a changed item, a bar on the left marks each part that changed, so the eye finds changes without reading labels. Each kind differs in line style as well as color, so it doesn't depend on telling red from green: changed, the most common, is a plain solid amber line; added is a dotted green line and removed a dashed red line. Removed text is also struck through, and status symbols differ in shape: a small square with a plus (added), a dot (changed) or a minus (removed); unchanged items have no symbol. Neighboring parts that changed the same way share one bar.
- **New and removed items** are marked as a whole instead: a NEW or REMOVED badge, and a tinted background with a border around the item (solid for new, dashed for removed). A new type and its new methods form one group, and the badge appears once, on the type; inside a new module only the module has it.
  - The signature block gets a bar when the signature changed. An unchanged signature, shown only for reference, is drawn muted and outlined instead.
  - Docs are compared paragraph by paragraph (lists and code blocks count as one paragraph). Changed and added paragraphs get a bar; removed paragraphs are shown struck through. When a paragraph changed only a few words, the words are marked inside it (inserted underlined, removed struck through). This is done only when it can't change how the Markdown renders: not for changes to link text or targets, Markdown syntax, the start of a line, or code blocks. Otherwise the previous text of the paragraph can be expanded. **Compare docs side by side** opens both versions next to each other, with changed paragraphs aligned.
  - After the docs, a line such as **Body changed +9 −6** expands to the source diff. A small change (at most 4 changed lines) is shown right away: the changed lines with two lines of context, and the whole source behind a toggle.
  - In source diffs, every resolved name links to its item, on added, removed and unchanged lines. A name of an item the PR adds is tagged **new**, and a call of a function or method the PR changes is tagged **changed** (not a recursive call, and not names of changed types, which would be everywhere), so the callees that need a review stand out. In review mode, the tag gets a ✓ once that item is reviewed.
  - A line whose text didn't change but whose names now refer to other items (a call that now resolves to a new helper of the same name, which shadows a glob import in a test module) counts as a changed line: it is shown removed and added, with what the name refers to now and before above the diff, and the summary says "(a name refers to another item)". Such a name is what makes an item with an unchanged text count as changed.
  - Items whose only change is the same set of such names (8 tests that all call a new test helper instead of the function it shadows) can be approved together: their review buttons say "Same change as 7 other items" and offer **Approve all 8** (also the `a` key) next to **Only this**. Approving all gives the others that are still open an approval without a comment. Request changes and Comment apply to the one item only, since such a remark is usually about that item. Each item keeps its own mark, so one that changes again later needs a review of its own.
  - **Reformatting** is not shown as a change: lines that only got wrapped differently, as when rustfmt splits a call or a struct literal over several lines, are compared token by token (like [difftastic](https://difftastic.wilfred.me.uk/)). If they hold the same tokens apart from whitespace and trailing commas, they are shown once, in their new form, as unchanged lines with a dotted rule on the left, and they are not counted, not reviewed as hunks, and don't open the diff. A line comment is compared as one token, so rewrapping one still shows. Rewrapped lines that also gained or lost a few tokens, as when a call gets one more argument and rustfmt then splits it over several lines, are shown the same way, in their new form, with only those tokens marked: added ones in green (a line that is all new, such as the new argument's, as an added line), removed ones struck out where they were, and a `~` on lines with changed tokens. These count as added or removed lines and are reviewed as a change, and all of the call or literal stays in view. This only applies when the line diff replaces some lines with a different number of others, and most of their tokens stay the same; otherwise it is a plain line diff. The summary says "(reformatting hidden)"; the setting **Hide reformatting** shows the plain line diff instead.
  - **Shortened or spelled-out paths** are no change either: when `std::process::Command::new` becomes `Command::new` because the PR adds `use std::process::Command`, or `crate::m::helper()` becomes `helper()` with a new `use m::helper`, and the path resolves to the same item in both versions, the line is shown as a reformatted line, in its new form, with the removed segments struck out thinly and the added ones underlined with dots, both in the muted text color. The line is not counted and not reviewed as a hunk, also when it is the only line that changed (unlike reformatting, the two versions can have as many lines). This uses the same name resolution as the rest of the analysis, so it errs on the side of a change: a path that now resolves to another item of the same name (a new import that shadows the old one), or that can't be resolved (a glob import of another crate might bring the name), stays a change. Names from the prelude count as their `core` or `alloc` paths, so `std::string::String` → `String` also stays a change. The setting **Hide reformatting** shows these lines as a plain line diff, too.
  - **Public paths**: an item that becomes public under a new path, for example through a new `pub use`, or loses a public path, is a change: "+ now public as `crate::Op`", "− no longer public as `crate::Parser`".
  - Items moved to another module are marked as *moved*, also when they were edited while moving: an item is paired with the one of the same kind and name (and parent type) that disappeared elsewhere, if that is the only candidate on both sides and at least half of its code is the same. Its changes are then shown as for any changed item. If only formatting, comments or import style changed, the item is marked *formatting only* and counts as unchanged.
  - **Moved lines**: code moved between items, for example into an extracted helper, is marked as moved instead of as removed and added (like `git diff --color-moved`). A block of removed lines that reappears among the added lines of another item, or elsewhere in the same item, the same apart from whitespace and with at least 20 letters and digits, keeps its − or + but gets its own color and a note on its first line that links to the other end ("moved to `Parser::next_op`, line 47"). The diff's summary counts the moved lines. Lines that were only indented differently are not counted as moved.
- **Settings** (⚙ in the header, remembered per browser): source diffs inline or side by side, hiding whitespace-only changes (like GitHub), hiding reformatting (on by default, see above), and the code font and size. The default font is Iosevka, embedded in the page; ligatures are off so that `->` and `=>` show as written.
- **Private fields**: seen from outside its module, a type is shown as rustdoc shows it, with private fields hidden. An expandable "Full definition" section below it shows every field, with a diff if the definition changed.
- **Signature layout**: long function signatures are broken into lines the way rustfmt does (one parameter per line, `where` predicates on their own lines), never soft-wrapped.
- **Signature diffs**: a changed signature is diffed by structure, not text.
  - Parameters, generic parameters, where-clauses, fields and variants are matched by name, so reordering or renaming one doesn't scramble the rest.
  - Types are compared as trees: `f64` → `Result<f64, Error>` shows one green box around the new wrapper, with the kept `f64` inside; unwrapping gets a dashed red box.
  - Under the signature, one note per change says what changed, e.g. "parameter `env: &Env` added" or "return type wrapped in `Result<_, Error>`". Hovering a part of a change, or its note, highlights everything that belongs to it.
  - A note about an added, changed or removed field or variant shows its doc comment (for a removed one, the old one): the first paragraph, with the rest behind **More**.
  - Seen from outside the defining module, the public form of the definition is diffed, and a change to private fields only is noted as such. Signatures the analysis can't parse this way (traits, type aliases, …) fall back to a token-level diff.
- **Normalized names**: paths are shortened to what a reader needs (`crate::ast::Expr` → `Expr`). Every name links to its item, and hovering a name shows its fully qualified path.
- **Canvas awareness**: a name whose item is already on the canvas is highlighted, and hovering it outlines that card.
- **Source on demand**: each card has a collapsible source view, shown as a diff against the base version when the item changed.
- **GitHub ↗**: for a pull request, every changed item (in the lists and on its card) and every separate change in its source diff links to its line in the pull request's *Files changed* view on GitHub: the item's first changed line, or the change's first changed line. The page builds the link itself (`/pull/N/files#diff-<SHA-256 of the path>R<line>`, `L` for a removed line), so it works without a token. Lines that GitHub's diff doesn't show get no link.
- **Standard library and dependencies**: names from outside the analyzed crates link to a read-only card with their declaration and docs, as rust-analyzer describes them, plus a link to their documentation online. Only the items the analyzed code names are looked up, not whole crates, so this adds little time.

## Review mode

Review mode is on when the page opens, for going through a PR one item at a time. **Exit review**, at the end of the review bar, hides the controls again and keeps your marks, and **Start review** in the header turns them back on. The page remembers the choice:

- Every added, changed or removed item (functions, methods, types, trait impls, …) and every file listed under "Changed files" or "Dependencies and package settings" gets the three choices of a GitHub review, on the overview, the module pages and canvas cards: **✓ Approve**, **✗ Request changes** and **✎ Comment**. Approve marks the item and moves to the next one without a verdict, in call order: first a changed item that no other changed item calls or uses, then the changed items it calls (also through unchanged functions in between), depth-first in the order its body calls them, then the next such item. Types (and constants, statics, …) come after the functions that use them: once the functions reached from such an item are done, the changed types they use follow, each with its impls. So a private struct comes after the public function and the helpers that build it, not before them. Items are taken in reading order where calls don't decide, and files come last. The next item is shown where it is listed: on the same page if it is there, else on its module's page (or, on the canvas, as a new card next to its caller). Approve moves on only from an item that the review steps went to (**Next ▸**, a key, or the verdict before). An item opened from a link instead, such as a function in a call graph, stays, and a **Next:** row under its verdict suggests where to go: its changed callers and callees that still need a review, **◂ Call graph** first (its graph on the overview), then **Next unreviewed ▸**. The other two first ask for a comment (Markdown; Ctrl+Enter saves). **Next ▸** in the header, or the `j` key, moves on without a verdict.
- A changed item whose source diff has several separate changes (hunks, between folded unchanged lines) can also be reviewed hunk by hunk: each hunk is a box with its own **Approve**, **Request changes** and **Comment** at the top, and moves on to the item's next hunk. An approved hunk gets a thick left edge and a tinted bar, so the hunks still to review stand out. When every hunk has a verdict, the item gets one too (changes requested if any hunk needs them, else commented if any has a comment, else approved). A hunk's mark depends only on its changed lines, so after new commits only the hunks that changed need a review again. Posted to GitHub, a comment on a hunk covers that hunk's lines (see below).
- A comment can also go on chosen lines of a source diff, as on GitHub: in review mode, click a line's number to select it, and Shift+click another one to select the lines between, unified or side by side. The bar under the selection offers **Comment** and **Request changes**. The comment shows under its last line, with a stripe along its lines, and can be edited or removed there. It gives no verdict to its item or hunk, which still need their own; a requested change only makes **Finish review…** suggest requesting changes. Posted to GitHub, it is an inline comment on exactly those lines, from a removed line to an added one if the selection starts on one; if GitHub's diff doesn't show all of them within one of its hunks, it goes into the review's text with a link to them. The comments are kept with the review marks. Each remembers the text of its lines, so it follows them when a later revision moves them; if they changed (or their text now appears more than once in the item), it shows at the end of the item's diff as changed and is left out of the review.
- A reviewed item shows its verdict and the start of its comment everywhere it appears, also with review mode off, and its row is folded to one dimmed line. **▾ Expand** shows it whole again, **Edit** changes the verdict or the comment, and clicking the verdict removes it.
- The header shows how many of the PR's items and files have a verdict; in review mode the sidebar counts what is left per module (✓ when nothing is). **Marks…** copies, pastes or clears them (see below).
- Marks are saved in the browser's local storage, per pull request (for `git`, per repository or subdirectory; for `dirs`, per pair of directories; the page holds only a hash of their paths), so they carry over to a page generated again after new commits, as long as the browser opens it from the same address (see below for the action's pages). A mark remembers the item's diff: if the diff is different in the new page, the item shows **⚠ Changed since review** and counts as not reviewed.
- The PR's full page and its page of the changes since an earlier commit share their marks. A mark also remembers which change was reviewed, from which version of the item (or file) to which: a review on either page counts on the other where it covers what that page shows. Reviewing the whole PR covers the changes since any earlier commit. On the full page, an item counts as reviewed when the reviews add up from its base version to its current one, such as the whole PR reviewed at the earlier commit plus the changes since. Hunks share their marks when both pages show the same change.
- GitHub serves each page the action uploads from a storage host of its own (`productionresultssaN.blob.core.windows.net`, usually with a different `N` for each run), and browsers keep local storage per host. So marks made on one Rust Semantic Review comment's pages don't show on the next comment's pages. The full page and the changes-since page of one comment share a host, so they share marks. Marks travel to a later comment's page in two ways:
  - A review posted with **Finish review…** ends with the marks, in a collapsed "Review marks" section: a code block with one line per mark (`mark HASH ID` with the hash of the diff it had, `change full|since FROM TO ID` for a reviewed change, `verdict changes|comment ID`). It leaves out the PR and the comments, which the review has, and the reviewed versions, which would make the command long. The action reads the PR's reviews and puts the latest marks of each reviewer into the page. A page without marks of the PR then offers **Load marks from NAME's review** in the review bar, and **Marks…** lists them all. Marks loaded from a review can't show what changed since then (**Show changes**); the page of the changes since the previous comment shows that.
  - **Marks…** → **Copy marks** copies them (with the reviewed versions) as text, and **Load marks** under "Paste from another page" adds them on another page. Marks of another PR are refused.

  Loaded marks are added where the page has none of its own for the same item, file or hunk.
- A mark also keeps the version that was reviewed. **Show changes** next to a stale mark compares it with the current one: a line diff of the PR's version since the review, of the base version if that changed too (after a rebase), and a list of anything else that differs (status, public paths, what the signature's names refer to). For a file outside the Rust analysis, only the parts its diff shows are kept, except for Markdown files, which are kept whole. Marks made by pages from before this was added have no saved version; the dialog says so.
- **Finish review…** sums up the verdicts and comments, suggests an overall verdict (request changes if any item needs them, approve if every item is approved, else comment) and takes a summary. For a pull request, it offers one command to copy and run, which posts the review (verdict, summary and inline comments) with the GitHub CLI: `printf '%s' '{…}' | gh api --method POST repos/OWNER/REPO/pulls/NUMBER/reviews --input -`. The JSON is in the form [GitHub's API for creating a review](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request) takes, and is quoted so that the command works the same in bash, zsh and fish. GitHub doesn't let you approve your own PR, so for an approval the command falls back to a comment review that starts with "Approved." when GitHub refuses the approval. The page itself never talks to GitHub and holds no token, since anyone who can open it could read one; `gh` uses your own login. Each comment is an inline comment on the lines of its item that GitHub's diff shows, on the commit the page was generated for: a comment on a hunk, or on an item with only one change, covers that change's added lines (or, without any, its removed lines on the base side), as far as one hunk of GitHub's diff holds them, since GitHub takes a comment on several lines only within one. A comment on an added or removed item, or on an item with several changes, goes on its first added line, else its first removed line, else a line of context, and one on a file outside the Rust analysis on the first added line of its first change (else that change's first removed line). Comments that fit on no line (a binary file, an item without a diff line nearby) go into the review's text, with a link to their lines on GitHub, and comments on items that changed since you reviewed them are left out. GitHub refuses the whole review if one comment is on a line its diff doesn't show, which can happen where its diff differs from the page's (a renamed file, a page made with `--base` or `--since`, or a change that the two diff algorithms place differently). So the command then posts the review again with every comment in its text, linked to its lines; for an approval, after trying the comment review that starts with "Approved." with inline comments first. The review can also be copied as Markdown, for an ordinary comment, with a horizontal rule before each comment and links to the lines at the compared commits (marked “(base)” for the base's lines). Without a terminal, as on a phone, **Copy and open the PR** copies the Markdown and opens the PR's page on GitHub in the same tap, to paste it into the comment box there, or into the review of the Files changed tab to approve or request changes. GitHub has no link that fills in a comment on an existing PR (its query parameters only fill in new issues and PRs), so the text has to be pasted. On a touch screen, these copy buttons come before the command, since a phone has no terminal to run it in.
- **Keyboard**, in review mode (unless typing in a field): `j` goes to the next unreviewed item and `k` to the previous item in review order (reviewed or not, shown whole again); `n` and `p` move to the item's next and previous hunk (`n` after the last one goes on to the next item); `a`, `r` and `c` approve, request changes on or comment on the current item (or the current hunk); `Enter` follows the current item's first reference to a new or changed item that isn't reviewed yet (the ones its source diff tags), and shows that item; `?` (or the **?** button in the review bar) shows and hides the list of shortcuts. The current item is the one that **Next ▸**, a verdict or a key last went to, as long as the open view shows it, else the first unreviewed one in view. It has a blue outline. When it was scrolled out of view, the first `a`, `r` or `c` only scrolls back to it, and holding the key down marks only one item. The keys never use Ctrl, Alt or ⌘, so they don't take any of the browser's shortcuts.
- Nothing leaves the browser: marks are not shared between browsers or people.

## Commit filter

For a pull request or a `git` range, the **Commits** menu in the header shows only what one commit changed, like GitHub's view of a single commit. Every page then lists only the items and files that commit touched, and a note at the top names the commit, with **Show all commits** to go back.

- Which items a commit touched is worked out with `git blame` when the page is built. An item's added lines are blamed in the PR's version (the commit that last wrote each line), and its removed lines in the base with `git blame --reverse` (the commit after the last one that still had the line). A commit counts an item if it wrote one of its added lines that is still there, or removed one of its base lines. A line that a later commit rewrote counts only for that later commit.
- A file counts for every commit that modified it, whether or not that change survives.
- Items keep their whole change from the PR's base to its head, not only the commit's part, since the page holds no other versions.
- Some changed items have no changed line of their own, for example an item whose only change is a public path that a `pub use` elsewhere added. These are listed under **Changes no commit was found for**.
- Merge commits are listed but not traced. Ranges with more than 250 commits get no filter (a warning says so), since each commit needs its own blame runs, which fetch old file versions on demand.

## Review threads

For a pull request, the page also shows the PR's review threads on GitHub as they were when the page was built (fetched with `gh api graphql`, so the action's token or your own `gh` login), open and resolved:

- Each thread appears under the line it is on, in the source diff of the changed item that contains that line (the innermost one, so a method rather than its impl), and so inside the hunk it belongs to. A thread on a removed line is shown after that line. Lines with a thread are never folded away. The source summary counts the item's threads (**💬 2 review threads, 1 open**), and a source diff with an open thread starts expanded. Open threads start expanded, resolved ones folded.
- Threads on a file outside the Rust analysis are listed on that file's card, with their lines.
- The overview lists every thread with its state, where it is and the start of its first comment. Threads that no item or file card shows, such as outdated ones (whose line is gone) or those on unchanged items, are shown there in full.
- Comments are rendered as Markdown the same way as the PR's description: raw HTML is shown as text and images only as their alt text, so the page still loads nothing from elsewhere. Each thread links to its conversation on GitHub.

The page holds a copy of the threads, so it can be read by everyone who can open it, which for the action is the same people who can read the PR. The threads are not updated after the page was built; build the page again to see new ones.

## Canvas

- Click any name to place its item next to the current card, with a connector between the two. The new card goes where its connectors to the cards already open (those that call or use it, and those it calls or uses) run cleanest without widening the canvas: usually right of the current card, but below it in the same column when another caller sits further left, so that this caller's connector doesn't run behind the current card. It takes the first free space in that column.
- **◂ callers** shows callers, to the left of the card, and **calls ▸** shows callees, to the right. **◂ used by** shows where a type or trait is used, broken down into signatures, fields, impls and bodies. These buttons are toggles: once clicked, a button is shown pressed, and a second click closes the cards it opened.
- Edges: solid for calls, dotted for uses. Every edge is resolved, never guessed. Edges between cards side by side run horizontally and vertically through the gap between them, each in a lane of its own, and end at their own point on the card's side, so that several edges into one card don't share an arrowhead. A call into a card above or below the caller in the same column leaves the caller at the call, runs beside the column and enters the callee's right side. A badge in a card's footer ("3 unresolved") counts the call sites in its body that could not be resolved, so a missing edge is visible; its tooltip says why.
- A card is as wide as the code it shows (signature, source, code in its docs), between 580 and 1000 pixels (1600 for a side-by-side diff), so that code formatted to 100 columns (rustfmt's default) needs no sideways scrolling in the default font. Drag a card's right edge to make it wider or narrower; a double click on the edge fits it to its code again. When a card gets wider (or taller), the cards right of it (or below it) move along, so that they don't overlap.
- Drag a card by its header onto another card's header to combine them into **tabs**. *members as tabs* opens all methods of a type in one tabbed card.
- **Viewing from** sets the module the canvas is looking from. Only items that are visible from that module, under Rust's privacy rules, are shown. Hidden callers and callees are counted in a badge ("2 private callers"); its tooltip names the modules they are private to, and a click views the canvas from that module.
- Cards of unchanged items (an unchanged callee, say) show only their signature. **docs & source ▾** expands one, **signature only ▴** folds it again.
- With a mouse, a press on code selects text, as usual, and a press next to it (after the end of a line, on the line numbers) moves the view like the background; the cursor shows which (a text cursor or a hand). A mostly sideways drag there scrolls code that is wider than its card.
- **Arrange by module** lays the cards out inside nested module frames, with each module's private items in a dashed zone.
- **↶ Undo** (or Ctrl+Z, ⌘Z) takes back the last change to the cards: a move, a resize, cards opened or closed, tabs combined, **Arrange by module** or **Clear**.
- Double-click a card's header (double-tap on a touch screen) to center the card and zoom to a comfortable reading size, with code at 16 pixels on screen. Each further double-click on the same card zooms one step closer (20, then 25 pixels); the one after the closest step goes back to the reading size. A card that doesn't fit the view at that zoom shows its top left corner. **Fit**, Ctrl+scroll or a pinch zoom out again.
- On a touch screen, one finger pans the view wherever it starts, also on a card, and two fingers zoom. A card follows the finger only after the finger rested on its header for about half a second, so that moving the view doesn't move cards by accident. A sideways swipe on code that is wider than its card scrolls the code. A card's right edge has a grip and resizes the card right away.

## Calls

The call graph one item at a time, made for phones, where the canvas needs a lot of panning and zooming. The focused item's card is in the middle, as on the canvas, with what calls it (**Called by**, and **Used by** for types and traits) above and what it calls (**Calls**) below. On a wide screen the three are side by side.
- Tap a caller, a callee or any name in the card to focus that item. The trail at the top lists the items focused before; tap one to go back to it. Each focus is a browser history entry, so Back works too.
- Each row shows the item's status, its module, and how many callers (↑) and callees (↓) it has in turn, so you can see where the graph goes on. Changed items come first; unchanged ones are dimmed. A long list shows up to 30 changed items and fills up to 12 rows with unchanged ones; **Show N more** under it shows the rest, until another item is focused.
- On a phone (up to 760 px wide), the links that elsewhere open the canvas open this view instead: **Open ▸** on the module pages, a name on a page that the page doesn't list, **Find item**, **Internal call graph ▸** (the module's changed items, to pick one from) and the public API impact's **Show callers ▸** (the item, whose callers lead up to the public API). **Open on canvas** still gets to the canvas.
- Without a focus, the view lists the changed functions, those that no changed item calls first, as places to start.
- Review buttons, Next ▸ and the review keys work as on the other views: after a verdict, the next unreviewed item is focused. While the view is open, **Find item** focuses the item it picks. **Open on canvas** places the focused item on the canvas.

## Structure view

How the change spreads over the modules, in two modes:
- **Module map** (default): the module tree as boxes, a parent above its children. Each box lists its changed items, exposed ones first and private ones below a dashed line; private modules have a dashed border. One arrow per pair of modules whose items call each other, labeled with the number of calls. Arrows run horizontally and vertically around the boxes, never through them, and leave and enter boxes at right angles; hovering a module highlights its arrows. With many arrows they stay faint until hovered. Long lists are cut after 8 items, with a link to the module page.
- **Matrix**: modules against modules; each cell counts the calls from the row's module into the column's that involve a change. Hovering a cell lists the calls, clicking it opens them on the canvas.

"uses" adds type uses to the calls, "all items" includes unchanged items. Drag the background to pan the view, as on the canvas; the mouse wheel scrolls it.
