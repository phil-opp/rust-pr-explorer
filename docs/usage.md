# Usage details

The [README](../README.md) has the commands and options. This page has the details.

## Command line

All commands write `rust-semantic-review.html` (change it with `-o`). Open that file in a browser. `--json analysis.json` also writes the raw analysis. `--syntax-only` skips the rust-analyzer step, which makes the run faster but leaves method calls and calls inside macros unresolved (see [Limitations](how-it-works.md#limitations)).

In a sandboxed environment, `--trust-project-code` (or `RUST_SEMANTIC_REVIEW_TRUST_PROJECT_CODE=1`) lets rust-analyzer run the project's build scripts and procedural macros. It then also resolves calls involving generated code, such as types from `include!(concat!(env!("OUT_DIR"), …))` or items produced by proc macros. See [Safety](how-it-works.md#safety).

This builds the dependencies' build scripts and proc macros with `cargo check`, which takes a while on a project with many dependencies. Both versions (and the "since" one) share one target directory, a temporary one by default. `--target-dir DIR` (or `RUST_SEMANTIC_REVIEW_TARGET_DIR`) keeps it between runs, so that a later run only rebuilds the workspace's own crates. On this repository: 47 s without trust, about 7 minutes with trust and an empty target directory, and about 2 minutes with a filled one (4 cores).

`--semver-checks` also runs [cargo-semver-checks](https://github.com/obi1kenobi/cargo-semver-checks) on the two versions (it must be installed: `cargo install cargo-semver-checks`) and adds what it finds to the SemVer labels (see [Overview](features.md#overview)). It compares the rustdoc JSON of both versions, so both must build, and building them runs the project's build scripts and procedural macros: like `--trust-project-code`, use it only in a sandbox. It doesn't turn on `--trust-project-code` for rust-analyzer: the two are separate options.

For `git`, the path may also be a subdirectory of the repository (then only that subdirectory is analyzed and listed) or a bare repository. For `dirs`, `target/` and `node_modules/` directories are skipped.

For `pr`, `--since <commit>` (a full commit id of the PR, e.g. one an earlier page showed) also writes a page of only what changed since that commit, next to the first with `-since` added to its name (`rust-semantic-review-since.html`, and `analysis-since.json` with `--json`). A plain diff from that commit would also show everything the base branch changed in between, once the PR merged it or was rebased onto it. So the base branch's changes since the commit's merge base are first applied to the commit (with `git merge-tree`), and the PR's head is compared with that. Where those changes conflict with the PR's, the files are taken from the PR's last merge, which holds the PR's own resolution, unless a commit of the PR changed them before that merge; then no page is written. When nothing changed but the base branch, no page is written either. The page's header says what it compares, and it shares its review marks with the PR's full page (see [Review mode](features.md#review-mode)). It has no commit filter, since commits are traced from the PR's base. The command prints `since: changes`, `since: none` or `since: unavailable (reason)` on stdout.

For `pr`, the repository is cloned without file contents (`--filter=blob:none`), and only the two revisions being compared are checked out. If the GitHub CLI (`gh`) is installed and logged in, `gh pr view` supplies the PR's title, description, base branch and its own branch; the page header then shows the repository, PR number and title, `base-branch ← pr-branch`, and the overview, under the title, a row each for the base and the PR's branch with the compared commits linked on GitHub, then the description (folded when it is longer than 20 lines). The description is rendered as Markdown like doc comments: raw HTML is shown as text, HTML comments (such as PR template instructions) are left out, and images show only their alt text, so the page loads nothing from elsewhere. Without `gh`, the title, description and PR branch are left out. `gh` also supplies the PR's review threads (see [Review threads](features.md#review-threads)). Without `--base`, the base is the merge base of the PR head and the PR's base branch (without `gh`: the default branch). For a PR that was already merged with a merge commit, the base is the state just before that merge.

The demo in `fixtures/demo` is a small calculator crate. Its "PR" adds variables (a new `env` module, a changed `evaluate` signature, new error variants), moves a helper between modules, extracts a helper method from the parser's loop, re-exports `ast::Op` at the crate root and drops the root re-export of `parser::Parser`, extends one doc comment (shown as a word diff), and changes some import styles and formatting. That last part does not show up as a change.

## GitHub Action

The action builds the tool, runs `pr` on the pull request (including its existing review threads) and uploads the page as a workflow artifact. The artifact is a single unzipped HTML file, so the link opens the page directly in the browser. The comment links the page with a one-line summary: how many Rust items changed, how many of them are public, and how many other files changed (those the page lists as files rather than items). The link is also in the job summary.

Every push that changes the PR gets a new comment, with two pages: all changes of the PR, and the changes since the commit that the previous Rust Semantic Review comment showed (built with `pr --since`, see [Command line](#command-line)). What the base branch changed in between is left out of the second page, so merging `main` into the PR or rebasing it doesn't show up there. A push that only merges the base branch or rebases onto it, and a re-run, update the previous comment instead of posting a new one. A new comment hides the previous Rust Semantic Review comment as outdated (if the workflow's bot posted it), so only the latest one stays expanded. Only Rust Semantic Review comments by the workflow's bot or by people with write access to the repository count as the previous one.

Build time: the built tool (about 12 MB) is cached under a hash of its sources and `rust-toolchain.toml`, per runner OS and architecture, so once a run has built it, later runs skip the build (in a repository that only uses the action, that is every run after the first, until the action's version changes). A build from scratch takes about 7 minutes, about 5 of them for the dependencies, mainly rust-analyzer. A cache saved on the default branch is the only one every pull request can read, so the `push` trigger above builds the tool there once per version; without it, each new pull request builds it itself. On a push, the action only builds and caches the tool. The tool is built with the `action` profile (see `Cargo.toml`), which is currently the same as `release`.

The build's dependencies are not cached by default: they take about 200 MB of the repository's cache storage (10 GB per repository, shared with other workflows), for a build that happens only once per version of the action. `cache-dependencies: true` caches them too, saved on the default branch (see `save-cache`), so that a new version builds only the tool's own crates. To keep the action out of the cache entirely, set `cache: false`: every run then builds the tool from scratch.

Who can open the page: anyone logged in to GitHub with access to the repository. In a public repository anyone can read the comment, but GitHub serves artifacts only to people who are signed in. The page expires with the run's artifacts (90 days unless the repository sets otherwise, or the `retention-days` input). The comment shows the date when the workflow has `actions: read` permission (to read the artifact's expiry) or sets `retention-days`.

Inputs: `comment: false` leaves out the comment, `comment: workflow-run` leaves it to a second workflow (see [Pull requests from forks](#pull-requests-from-forks)), `syntax-only: true` skips rust-analyzer, `semver-checks: true` adds cargo-semver-checks (see below), and `pr` and `repository` pick another pull request (by default the one that triggered the workflow). The `page-url` output is the link.

Under `pull_request`, the action runs in trusted mode by default (`trust-project-code: auto`): it passes `--trust-project-code`, so calls into code that build scripts and proc macros generate resolve too. That runs the PR's code with the job's token, as a CI job that runs the PR's tests does. Under `pull_request` that is no new risk: a PR from a fork gets a read-only token and no secrets, and a PR from a branch of the repository can change the workflow itself anyway. On a self-hosted runner, that means the build scripts of PRs from forks run on that machine, as they do for any CI job that builds PRs; set `trust-project-code: false` if the runner doesn't already run PR code. When another event analyzes a PR (e.g. `workflow_dispatch` with the `pr` input), whose token may be able to write, `auto` turns it off with a notice; an explicit `true` turns it on there. Under `pull_request_target`, whose token can write and which has the repository's secrets also on PRs from forks, the action refuses `true`. With `trust-project-code: false` the action never builds or runs the PR's code.

Trusted mode builds the build scripts and proc macros of the PR's dependencies, on every run unless `cache-target: true` caches the analysis' cargo target directory: keyed by the toolchain and the checked out `Cargo.lock` files and saved only on the default branch (see `save-cache`), and on a push to the default branch filled by analyzing the checked out repository. It is off by default because the directory can take several GB of the repository's 10 GB of cache storage for a large workspace, which pushes out other workflows' caches. This repository's workflow also sets `RUST_SEMANTIC_REVIEW_STUB_VIEWER=1`, so its build script skips the viewer's wasm build during the analysis (see `build.rs`). With that, a trusted run here takes about 75 s with the cache and 6 minutes without it, against 48 s untrusted, and the cache is about 1.8 GB of the repository's 10 GB.

`semver-checks: true` installs a prebuilt cargo-semver-checks and runs the tool with `--semver-checks`, which builds both versions and so runs the PR's build scripts and procedural macros, as any CI job that builds or tests the PR does, and it is refused under `pull_request_target` for the same reasons. It is off by default because of its cost. Both versions and their dependencies are built for docs, and nothing of that build is cached between runs. Measured locally on 4 cores (as many as GitHub's standard runner), without caches:

| Crate | Without | With `--semver-checks` |
|---|---|---|
| `fixtures/demo` (no dependencies) | 9 s | 10 s |
| `semver` 1.0.22 → 1.0.23 (no dependencies) | 10 s | 15 s |
| `log` 0.4.21 → 0.4.22 (optional dependencies; built with default features after the first attempt fails) | 16 s | 26 s |
| this repository, PR #48 (rust-analyzer, syn, wasm-bindgen, …) | 52 s | 97 s |

Installing the prebuilt binary adds a few seconds. For a small crate it is cheap; for a crate with heavy dependencies it roughly doubles the analysis. It is independent of `trust-project-code`.

On a PR from a fork, the token GitHub gives the workflow is read-only, so the page is built and uploaded but the comment fails with a warning; the link is still in the job summary, and the setup below posts the comment.

### Pull requests from forks

When the action can't post the comment (with `comment: true`, the default), or never tries (with `comment: workflow-run`), it uploads what the comment needs as the `rust-semantic-review-comment` artifact (the PR number, the analyzed commit, the previous comment's commit, the outcome of `--since`, and the numbers of the summaries). A second workflow, triggered by `workflow_run` when the first one completes, posts the comment with the comment-only action `phil-opp/rust-semantic-review/comment` (see the README for both workflows). `workflow_run` runs the workflow file from the default branch, with a token that can write also when the first run was for a fork. The comment-only action never checks out or runs the PR's code, and it builds nothing: it only uses `gh`, `jq` and `unzip`.

Under `pull_request`, a PR from a fork can change the first workflow and the action, so everything in its artifacts is untrusted. The comment-only action:

- posts only for runs of `pull_request` events that succeeded;
- takes the PR number from the artifact, but only posts if that PR's head is the run's commit (`workflow_run.head_sha`) in the run's head repository, which also skips the comment of a run that a newer push overtook;
- accepts the commits only as full hashes and the counts only as numbers, and writes the summaries itself from those numbers;
- links the pages by the IDs of the artifacts of that run, found by their names, never by a URL from the artifact;
- finds the previous comment itself, the same way the action does (only Rust Semantic Review comments by the bot or by people with write access), and uses the page of the changes since then only if the analysis started from the same commit;
- keeps only letters, digits and a few punctuation characters of the reason why the changes since the previous comment couldn't be shown, so that it can't add links, mentions or markup.

Updating the previous comment on a push that only merged the base branch, and hiding the previous comment when a new one is posted, work as with `comment: true`. Both need the workflow's bot to have posted the earlier comments, so switching to this setup keeps working with the comments posted before. Give the second workflow a `concurrency` group per PR branch (as this repository's `.github/workflows/rust-semantic-review-comment.yml` does), so that two runs don't both post a new comment after the same previous one. A `workflow_run` workflow only runs once it is on the default branch, so the PR that adds it gets no comment.
